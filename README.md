# GraveHub — модульний фронтенд

Цей архів містить лише frontend. Бекенд не змінюється.

## Запуск у Git Bash

Відкрий папку gravehub-frontend поруч із package.json:

```bash
npm install
cp .env.example .env
npm run dev -- --port 5173 --strictPort
```

У `.env` встанови `VITE_API_URL=http://localhost:3000`. Відкрий http://localhost:5173, тримай бекенд запущеним окремо. Без адреси API показується екран налаштування; вигаданий користувач автоматично не створюється. .env та секретів в архіві немає. Після зміни адреси перезапусти Vite.

## Структура

- src/main.tsx — точка входу.
- src/components/App.tsx — стан застосунку та маршрути.
- src/components/Context.tsx, useApp.tsx, Ctx.tsx — контекст і типи.
- src/components/Auth.tsx, Profile.tsx — авторизація та ролі.
- src/components/NewContract.tsx, Details.tsx, Proposals.tsx — сценарії контрактів.
- src/components/new-AdvancedMarket.tsx, new-Filters.tsx — серверний пошук замовлень customer/employee.
- src/components/new-Directory.tsx — пошук виконавців.
- src/components/Badge.tsx, Pagination.tsx, Field.tsx тощо — спільні компоненти.
- src/api.ts — Axios, типи контрактів, сесія в пам’яті, single-flight refresh.
- src/new-api.ts — нормалізація варіантів назв послуг у відповіді пошуку виконавців.
- src/ErrorBoundary.tsx — резервний екран замість білого екрана при помилці рендерингу.
- tests/contracts.mjs — автоматичні перевірки авторизації.

Кожен компонент у власному файлі; основний main.tsx не містить сторінок. Для великих сценаріїв Details/App залишено окремі компоненти у кілька сотень рядків.

## Виправлення

Координати — цілі числа ≥0, step=1, перевірка перед POST. Коментарі й відгуки обрізаються та відхиляються, якщо містять лише пробіли. Відомі ролі та ім’я з реєстрації зберігаються в пам’яті між refresh/switch-mode. Відповідь /auth/roles/* застосовується без додаткового refresh. Для неправильного пароля окреме повідомлення. Для customer пошук, послуги, регіон, бюджети, сортування та сторінки передаються серверу; непідтримуваний status не відправляється. Для employee є окремий статус cancelled.

Повторне завантаження деталей очищує стару помилку, запити пропозицій мають захист від оновлення після завершення ефекту. Тости мають нейтральну іконку замість помилкової галочки успіху й очищують попередній таймер. Пропозиції без доступного контракту не створюють посилань /undefined чи переходів до недоступного чужого замовлення. Перед повторним поданням перевіряється власний список пропозицій; сервер усе одно остаточно перевіряє конкуренцію/409.

У пропозиціях ім’я не вигадується: якщо сервер не надав його, відображається ID профілю й кількість завершених робіт. Масив послуг у пошуку нормалізується з specialization/specializations/services. Якщо reviewsCount=0 — «Без відгуків»; якщо сервер не надав лічильника, його не можна достовірно відновити з rating.

Відгуки в модальному вікні очищуються перед завантаженням; додано dialog, aria-modal, закриття Esc/фоном і утримання клавіатурного фокуса. Є повернення після входу на запитану сторінку. Прибрані недосяжні стартові assets, старі tsconfig-проєкти, terminal.local та прив’язка dev-сервера до 0.0.0.0.

## Межі API, які фронтенд не може вирішити сам

1. Токен містить лише sub і role. Без endpoint профілю неможливо відновити повний список ролей, ім’я та email після повного перезавантаження. У кабінеті показано «Відомі ролі» й пояснення. Спробуй перемкнути інший режим: тільки сервер може підтвердити доступ. Форма запиту нової ролі показується для підтверджено відсутньої ролі (403 на перемикання) або якщо повний набір ролей відомий після реєстрації. Локальні дані не є дозволом: сервер перевіряє кожен запит.
2. /employees/:id не використовується. Профіль відкривається з даних пошуку, відгуки — через документований /employees/:id/reviews. Пряме відкриття профілю після перезавантаження пропонує повернутися до пошуку.
3. /cemeteries та /plots не викликаються; їхні сторінки й непрацюючу навігацію вилучено з робочого сценарію. Це свідомо вимкнені функції, поки endpoint не підтверджено документацією. Купівля/кредит не імітуються.
4. Загальна кількість замовлень береться з total, статусні числа огляду стосуються лише поточної сторінки й підписані відповідно. Агрегати всіх статусів вимагають окремого API.
5. Наявність ролі визначається сервером, а не довірою до розкодованого JWT на фронті. Дані сесії не записуються в localStorage/sessionStorage.

Деякі внутрішні типи/контекстні поля старого демо залишено для сумісності сторінок; користувацький автоматичний деморежим вимкнено. Це не повне переписування предметної логіки бекенду.

## Перевірки

```bash
npm run build
npm run lint
npm test
```

Тести: credentials, Bearer/public headers, одночасні 401 та один refresh, повтор запитів, заміна токена, збереження відомих ролей/імені, повідомлення логіну, meta pagination, завершення сесії. esbuild — пряма devDependency. Lint перевіряє синтаксис TypeScript і заборону explicit any; це не повний аудит React hooks.

Збірка, lint і тести виконані. Браузерна перевірка та наскрізний цикл із живим бекендом/PostgreSQL у цій ітерації не виконувалися. Бекенд, Docker і файли його налаштувань в архів не включено.

## Завантаження у свій GitHub

Скопіюй вміст папки з архіву до локального frontend-репозиторію, збережи його .git та власний .env. Видали стару папку src після резервної копії, щоб не залишити дублікати старих компонентів, і скопіюй нову src. Потім:

```bash
git switch -c refactor/modular-frontend
npm install
npm run build
npm test
git add src tests package.json package-lock.json tsconfig.json vite.config.ts eslint.config.js README.md .gitignore .env.example
git status
git commit -m "Refactor frontend into modules and fix API handling"
git push -u origin refactor/modular-frontend
```

Перед commit переконайся, що .env не підготовлений до додавання. У GitHub створи Pull Request у свою головну гілку.
